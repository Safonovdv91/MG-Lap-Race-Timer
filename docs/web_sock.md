# Архитектура реального времени с WebSockets

Этот документ описывает архитектуру обмена данными между таймером (ESP32) и клиентскими устройствами (веб-браузер, другие ESP32) с использованием технологии WebSocket. Эта архитектура была внедрена для замены устаревшей и медленной модели опроса по HTTP (HTTP Polling).

## 1. Обзор архитектуры

Основная идея — переход от модели "клиент спрашивает" (pull) к модели "сервер сообщает" (push).

*   **Сервер (ESP32-приемник):** Работает как WebSocket-сервер. Он больше не ждет периодических запросов от клиентов. Вместо этого, он **мгновенно рассылает (push) пакеты данных** всем подключенным клиентам в тот момент, когда в системе происходит значимое событие (старт таймера, финиш, смена режима).

*   **Клиент (Браузер или другая ESP32):** Выступает в роли WebSocket-клиента. При запуске он устанавливает **одно постоянное соединение** с сервером и затем пассивно "слушает" входящие сообщения. Это гораздо эффективнее, чем постоянно отправлять запросы.

*   **Формат данных (JSON):** Обмен данными происходит с помощью стандартизированных JSON-сообщений, которые содержат полное состояние таймера в текущий момент времени.

## 2. Изменения в коде

### Конфигурация (`platformio.ini`)

1.  **Добавлена библиотека:** В `lib_deps` для окружения `Receiver-RX` была добавлена зависимость `links2004/WebSockets@^2.4.1`.
2.  **Обновлен фильтр сборки:** В `src_filter` был добавлен файл `+<websocket_handlers.cpp>`, чтобы компилятор включил его в прошивку.

### Бэкенд (Прошивка ESP32)

#### Новые файлы: `websocket_handlers.cpp` и `websocket_handlers.h`

Чтобы не загромождать основной код, вся логика работы с WebSocket вынесена в эти файлы.

*   `ws_init()`: Инициализирует WebSocket-сервер на порту 81.
*   `ws_loop()`: Эту функцию необходимо постоянно вызывать в главном цикле `loop()` для обработки событий WebSocket (подключения, отключения, прием данных).
*   `onWebSocketEvent()`: Внутренняя функция-обработчик. Она вызывается, когда клиент подключается или отключается. При новом подключении она немедленно отправляет ему текущее состояние таймера.
*   `ws_broadcast_data()`: **Ключевая функция.** Она собирает все актуальные данные (режим, время, статус, история, заряд батарей) в один JSON-объект и рассылает его всем подключенным клиентам.

#### Интеграция (`receiver_main.cpp`)

*   В `setup()` теперь вызывается `ws_init()` для запуска WebSocket-сервера.
*   В `loop()` теперь постоянно вызывается `ws_loop()`.
*   URL `/api/v1/data` и его обработчик `handleData()` были полностью удалены за ненадобностью.

#### Отправка данных (`measurements.cpp`)

Это "сердце" новой системы. Функция `ws_broadcast_data()` теперь вызывается в следующие моменты:

1.  **При смене состояния:** Сразу после того, как таймер переходит в новое состояние (`READY`, `RUNNING`, `DISPLAY`). Это обеспечивает мгновенную реакцию интерфейса.
2.  **Во время замера:** Пока таймер находится в состоянии `RUNNING`, данные отправляются каждые **100 мс**. Это создает эффект "живого" обновления времени на экране без слишком большой нагрузки на сеть.
3.  **При подключении нового клиента:** Чтобы новый пользователь сразу увидел актуальное состояние.

### Фронтенд (`script.js`)

Клиентский скрипт был полностью переписан.

*   **Отказ от `fetch`:** Весь механизм `setInterval` и `fetch`, который раньше опрашивал сервер каждые 300 мс, удален.
*   **Установка соединения:** При загрузке страницы скрипт пытается установить WebSocket-соединение с сервером по адресу `ws://{hostname}:81/`.
*   **Обработка событий:**
    *   `onopen`: Соединение успешно установлено.
    *   `onclose`: Соединение потеряно. Скрипт автоматически пытается переподключиться каждые 2 секунды.
    *   `onmessage`: **Самая главная часть.** Эта функция вызывается каждый раз, когда от сервера приходит JSON-сообщение. Она парсит эти данные и обновляет ВЕСЬ интерфейс: цифровой дисплей, цветной индикатор статуса, историю кругов, индикаторы батарей.

## 3. Преимущества нового подхода

1.  **Низкая задержка:** Реакция интерфейса на события практически мгновенная.
2.  **Высокая эффективность:** Нагрузка на процессор ESP32, сеть Wi-Fi и устройство клиента значительно снижена, так как данные передаются только по делу.
3.  **Масштабируемость:** Архитектура позволяет легко подключать несколько клиентов (несколько браузеров, другие ESP32), и все они будут получать данные одновременно и эффективно.

## 4. Как подключить вторую ESP32 с экраном

Благодаря новой архитектуре, это стало просто:

1.  На второй ESP32 нужно использовать ту же библиотеку `WebSockets` в режиме **клиента**.
2.  В коде нужно будет подключиться к Wi-Fi сети основного таймера.
3.  После этого установить WebSocket-соединение с IP-адресом основного таймера и портом 81.
4.  В цикле слушать входящие сообщения (`onmessage`), парсить JSON и выводить нужные данные (`value`, `timer_status` и т.д.) на подключенный дисплей.
